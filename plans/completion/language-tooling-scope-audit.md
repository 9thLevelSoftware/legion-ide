# S0-01i language tooling scope audit

## Inventory boundary and governing sources

This audit expands only `COMP-SCOPE-FAMILY-05` from committed baseline `043c1e1`. The aggregate is replaced by `COMP-LANG-001` through `COMP-LANG-013`; all product acceptance remains `unassessed`. The source family is language tooling. Navigation-specific quick-file, symbol, definition, references, and history journeys remain in the Navigation family; these rows cover language-server-backed semantic results and their live server/configuration workflow.

The approved family source states, verbatim, **“Language tooling”** (`docs/superpowers/specs/2026-09-04-product-completion-design.md`, “Required feature families”, family-05). The approved manual plan states **“Stage 2 — Rust, TypeScript/JavaScript, and Python complete workflows”** and requires the three-language support matrix, package/environment discovery, LSP, formatter, test runner, build/task, debug adapter, OS/version entries, representative fixture/project identity, and fixture hashes/provenance (`docs/superpowers/plans/2026-09-04-manual-language-completion.md`, S2-01). It requires app-owned provisioning and lifecycle, visible startup/failure/backoff/restart, preserved buffers, and diagnostics/completion/hover/definition/references/rename/format/code actions projected through the same desktop surfaces (S2-02). S2-03 requires every core language feature against a real supported server and multi-file edits through preview/apply/cancel/rollback proposal authority. The P2.F1.T5 wording separately names rename, format, code actions, and organize imports, so organize imports is retained explicitly in LANG-007. S2-04 requires build/test discovery, targeted and grouped execution, and actual process output/exit. S2-05 requires real debug adapters with launch/attach, breakpoint, step, variables, expression, console, terminate, crash recovery, and unavailable state. S2-06 requires packaged native journeys and canonical `EvidenceRun` records.

The traceability source (`docs/superpowers/plans/2026-09-04-completion-traceability.md`, P2.F1) names registry, rust-analyzer resolution/configuration/lifecycle, diagnostics, completion/hover/definition/references/symbols/inlay/code lenses/runnables, rename/format/code actions/organize imports, and call hierarchy. P2.F3 supplies build/test/debug workflow sources. The product design's “Finite supported configuration contracts” requires Rust, TS/JS, and Python toolchains/project types/LSP/test/debug/package discovery, multi-file navigation/refactor, and failure/restart behavior. These exact promises are normalized into independent rows below.

## Exact legacy deduplication

The aggregate replacement retains exact existing outcomes rather than duplicating them: `COMP-P2-F1-T1-1` (mock server product registry) maps to the registry portion of LANG-002; `COMP-P2-F1-T2-1` (rust-analyzer lifecycle) maps to LANG-004/LANG-008; `COMP-P2-F1-T3-1` (Rust diagnostics) maps to LANG-005; `COMP-P2-F1-T4-1` (LSP feature reachability) maps to LANG-005/LANG-006; `COMP-P2-F1-T5-1` (reviewable reversible rename) maps to LANG-007; and `COMP-P2-F1-T6-1` (call hierarchy) maps to LANG-006. Existing P2.F3 test/debug rows map to LANG-011/LANG-012 where identical. The narrower cross-language, configuration, real-server, failure-state, and EvidenceRun promises are independent and therefore have dedicated rows. Existing rows remain byte-for-byte unchanged.

The Python entry is deliberately classified as a gap: `LanguageServerRegistry::tier_two` points at `https://registry.example.invalid/pyright-1.1.400.tgz`, while committed `startup_session` is Rust-only. This is not evidence of a functioning Python server or download materializer. Likewise TS/JS registry declarations do not prove a desktop live-server route. All 13 rows retain `acceptance: unassessed`; this inventory does not claim S0 completion.
