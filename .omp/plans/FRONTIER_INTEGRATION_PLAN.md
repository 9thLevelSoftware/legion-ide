# Research-backed Legion integration plan

## Context
Integrate all improvements and enhancements identified in `plans/evidence/technology-review-and-frontier-opportunities.md`: reliable ordinary IDE workflows, evidence-linked change intelligence, counterexample-guided verification, verified refactoring search, capability-scoped structured local generation, and measured learned retrieval. The eight recorded correctness repairs are existing baseline work, not new frontier features. Preserve the native stack and proposal-mediated mutation authority; the deliverable is a dependency-ordered design, development, and implementation specification.

## Approach

### Confirmed design decisions

The user confirmed Q1–Q18 in the design interview and authorized their incorporation here. These are design commitments, not evidence of implementation or permission to provision tools, run repository code, or ship a feature.

| Decision | Agreed contract |
| --- | --- |
| Q1 — Work and shipping | Complete every investigation and implementation package, recording unsuccessful experiments honestly. Capability support and shipping require independent qualification; work completion alone is insufficient. |
| Q2 — Primary outcome | Help a developer understand and safely review a proposed change. Proof repair, refactoring search, and learned retrieval serve that journey. |
| Q3 — Advisory checks | Optional verification is advisory, including timeout or inconclusive results. Explicitly required checks must satisfy their requirements before application. |
| Q4 — Automatic work | Inexpensive local impact analysis refreshes automatically. Formal verification, AI repair, and learned retrieval require explicit activation within bounded budgets. |
| Q5 — First delivery | First deliver proposal inspection, affected-code analysis, existing tests against the proposed state, evidence staleness, and review/apply. Extend this journey with formal repair and learned retrieval afterward. |
| Q6 — Dirty inputs | Capture relevant unsaved buffers in the verification subject. If the combined state cannot be represented reliably, block verification with an explanation; never substitute disk contents or save edits implicitly. |
| Q7 — Requirement authority | Only explicit authorized workspace policy or a developer-attached proposal requirement makes a check mandatory. AI and verifier output cannot remove or weaken it. |
| Q8 — Activation budget | One activation authorizes its described operation and internal attempts/batches within aggregate limits. Stop visibly at the limit; expanding scope or budget requires a new activation. |
| Q9 — Independent delivery | Ship qualified capabilities independently while others remain experimental or unavailable. Preserve separate work, experiment, and support statuses; partial delivery does not complete the frontier program. |
| Q10 — Unknown impact | Unknown relationships expand verification to the declared workspace scope. If limits prevent that coverage, report incomplete coverage rather than silently narrowing it. |
| Q11 — Repository execution | Tests and build scripts require applicable workspace trust and execution permission. Confine writes to the staged workspace and approved scratch locations; unavailable isolation is explicit and never permits an implicit unsafe fallback. |
| Q12 — Apply and dirty state | Apply preserves unrelated dirty buffers. Evidence labels the combined proposed editor state and does not imply that a different resulting disk state was checked. |
| Q13 — Requirement changes | Removing or weakening a required check invalidates prior approval and requires fresh review. Workspace mandates change only through authorized workspace-policy changes. |
| Q14 — Experiments | Experimental features are disabled by default and separately activated. Privacy, isolation, and mutation protections are mandatory even when usefulness or performance remains unqualified. |
| Q15 — Approval scope | Approval binds to the exact proposal, required checks, and relevant editor/dependency state. Meaningful changes require renewed review; proven-independent changes may be ignored, unknown independence invalidates approval conservatively. |
| Q16 — Unavailable requirements | An unavailable required verifier blocks the affected proposal, not ordinary editing or unrelated proposals. Explain unmet requirements and supported options; no waiver or execution-environment switch is implicit. |
| Q17 — Cancellation | A cancellation request immediately disqualifies subsequent output. Show stopping until transport/worker termination is confirmed; failed termination is a visible execution fault. |
| Q18 — Acceptance targets | Establish representative baselines, then freeze performance and retrieval targets before acceptance-candidate evaluation. Correctness and authorization invariants remain strict; never lower targets retrospectively to pass a candidate. |

Delivery sequence: establish applicable F0 prerequisites, then integrate the necessary F1/F2/F3 work into the first complete Q5 journey, including Q11's isolated test execution. This first delivery must not depend on Kani, Verus, learned embeddings, or equality search. F8 qualification applies to each delivered capability; later F4–F7 extensions follow their actual technical dependencies. A completed negative experiment needs a recorded conclusion and independent review, not a fabricated pass. It can close experimental work while the associated capability remains unqualified; blocked or unfinished work remains open.

### F5 — Incremental independently verified refactoring
**Files:** new index `refactor_ir.rs`; protocol typed IR/request/outcome; worker equality-search/checker modules; app proposal translation; Cargo/policy/ADR gates.

Exclude general calls/custom operators/casts/division/shifts/checked arithmetic/floats/allocation/effects/unsafe/macros/I/O/concurrency. Validate actual primitive types/intrinsics, not spelling. Explicit wrapping semantics preserve width/overflow and cannot introduce/remove panics; excluded code is Unsupported.
2. Lower selected expression to typed IR bound to source range/snapshot/type-server/compiler/profile; validate source/IR round trip and preserve surrounding bindings/evaluation order. Immutable ruleset covers identities/constants/bitwise identities and valid commutativity/associativity of this wrapping algebra, never unchecked ordinary-integer reassociation.
3. Optional worker-only egglog3.0.0/default-features=false; qualify Rust1.92 build/license/policy before activation, no product MSRV bump/editor/UI dependency/new DB. Sandbox may gain protocol and optional engine dependencies only for this explicit worker under its accepted policy entry. Index emits protocol IR; worker does not gain app/project/index authority.
   Cargo activation: binary requires feature `verifier-worker` (optional protocol/serde/serde_json dependencies); `verified-refactor` adds pinned optional egglog and implies verifier-worker. Allocate approved sandbox->protocol policy only for worker DTOs. CI compiles/tests both feature sets with `cargo +1.92.0 check -p legion-sandbox --all-targets --features verified-refactor` and corresponding focused tests; absence of provisioned Kani is not a fake live-proof pass.
4. Separate retractable `ActiveRoot(root_id,version,term)` facts from reusable universally valid pure equalities. Matches must require the current root version and current-version reachable nodes; old nodes are eligible only after explicit reactivation within current-root top8 extraction, with all children eligible and in-scope. Enforce this in the egglog scheduler/versioned rule guards, not just final extraction filtering. Superseding a root deletes its membership and clears queued matches; it never attempts to undo union-find equalities. Class unions merge node-origin version sets deterministically but cannot make a dead root active. Variables use resolved declaration+binder-scope+type-semantic identities, not spelling or recycled slots; reuse across edits requires confirmed binder/type correspondence. Rebuild on domain/rule/type/compiler/privacy changes; no conditional workspace assumptions enter the reusable equality arena. Test deleted/shadowed binders, old queued matches and repeated edits: obsolete roots cannot match/reappear, while explicitly reactivated valid terms remain independently checked. Measure pruning's cost loss versus cold saturation.
   State lifetime: supervisor retains a sandboxed search-session worker across edits; disposable verifier subprocesses remain per job. Search cache owns only typed terms/version metadata, never raw source. Its entire retained arena/cache, not each individual root, shares the256MiB budget; compaction/rebuild preserves only active-version reachable terms. Root/type/rule/config keys isolate reuse; worker crash drops cache, restarts cold and invalidates unfinished results. ## Domain model and boundary scenarios

Use the root `GLOSSARY.md` for canonical terms. These definitions describe the proposed frontier model, not implemented capability or accepted readiness. `VerificationEnvelope` is the planned representation of verification evidence; existing `EvidenceRun` records qualification runs. Keep their identities and authority distinct. The confirmed decisions above govern delivery and authority; tool selection and concrete isolation implementation remain subject to the package-specific reviews and gates.

- **Subject versus attempt:** checking the same proposed overlay twice produces two verification runs for one verification subject. Changing a dependency, property, assumption, or checking condition changes the subject even if the proposed source text is identical.
- **Success versus applicability:** a dependency changes while a successful check is finishing. Preserve the historical outcome, mark its evidence stale, and prevent the late reply from restoring current applicability or bypassing apply preconditions.
- **Freshness versus coverage:** current Rust relationships are resolved, but dynamic dispatch leaves an unknown caller. Impact coverage remains partial; conservatively expand affected checks. Neither fresh relationships nor complete proposal-target enumeration establishes complete impact coverage.
- **Outcome versus witness:** a solver exhausts its budget without a validated witness. Report ResourceExhausted, not Disproved. An unsupported witness format must not be presented as a validated or replayed counterexample.
- **Availability versus truth:** retained metadata says a run proved a named property, but its transient witness/output is absent after restart. Show the artifact as unavailable; do not invent replay evidence or silently change the historical outcome. Re-establish applicability separately before treating evidence as current.
- **Verification versus authority:** an independently checked refactoring is still a workspace proposal. Rejection, changed target preconditions, or denied workspace policy prevents application regardless of proof success.
- **Product versus workspace candidate:** a qualification run evaluates a pinned Legion build and scenario/configuration. A verification run checks a proposed workspace subject. Neither qualifies the other; always qualify the word candidate with its kind.
- **Cancellation request versus completion:** a cancellation request is not evidence that transport or worker processes have stopped. Qualification observes actual termination within the required budget, and superseded output remains ineligible for use.
- **Syntax versus permission:** schema-valid AI output requests a forbidden path. Its syntax can pass while policy rejects the action; no proposal application follows from schema validity.
