## ACP external agents and MCP

- ACP exists as an optional, app-owned local command bridge: `crates/legion-app/src/acp_host.rs` (`AcpHostCommand`, `run_acp_host_proposal`) supervises a configured process with 30-second timeout, supplies sandbox/target paths and plan ID through environment variables, then reads a proposal file and wraps output as a `DelegatedTaskProposalGenerator` result (`provider_id: "acp.local-adapter"`). App wiring/configuration is in `crates/legion-app/src/lib.rs` (`set_acp_host_command`, `AttachAcpHost`, delegated task execution). Tests in `crates/legion-app/tests/delegated_task_integration.rs` cover command success, proposal mediation, background use, and failure projection. This is real local workflow integration but a narrow one-shot command/file adapter, not a general ACP protocol/session implementation.
- `plans/adrs/ADR-0043-acp-host-local-adapter-bridge.md` ratifies this local adapter boundary and says a separate ACP service/crate would need a new ADR. `plans/product-readiness-ledger.md` PR-ENT-002 explicitly says GP-4 does not implement ACP/external-agent interoperability. No separate ACP product-readiness row or broad external-agent interoperability acceptance is recorded in the current ledger.
- MCP is distinct and broader: existing MCP client/server registry, transport, tools/resources/prompts and permission/risk gates are exercised in `crates/legion-app/tests/legion_workflow_integration.rs`; the ledger’s M3 evidence row identifies MCP client GA. MCP support is not evidence that ACP interoperability exists, and ACP command execution is not an MCP server/client implementation.

## Inline and next-edit predictions

- There is a functioning product path: protocol request/result/freshness/lifecycle DTOs in `crates/legion-protocol/src/lib.rs` (`InlinePredictionRequestMetadata`, `InlinePredictionResult`, `InlinePredictionProjection`); app provider invocation and stale handling in `crates/legion-app/src/lib.rs` (`invoke_inline_prediction_provider`); desktop ghost text renderer in `crates/legion-desktop/src/view/ghost_text.rs` (`ghost_text_from_prediction`) and Assist UI/settings in `crates/legion-desktop/src/view.rs` (`next_edit_prediction_enabled`, “Next-edit predictions”). App and desktop workflow integration tests exist at `crates/legion-app/tests/assist_inline_prediction_workflow.rs` and `crates/legion-desktop/tests/assist_inline_prediction_workflow.rs`.
- Provider reality is mixed. `plans/evidence/production/WS-P0/T2-assist-real-provider.md` states `try_live_anthropic_inline_prediction` adapts a short chat completion because Anthropic has no inline-predict endpoint; `invoke_inline_prediction_provider` prefers live then falls back to `deterministic-local`. `plans/evidence/production/WS-P0/T0-A-ledger-claim-repair.md` and the PR-AI-001 row say the default desktop Assist/inline/chat path remains the deterministic fixture with placeholder outputs; real-model-by-default and keyring/provider wiring remain follow-on work. Thus UI/projection, lifecycle and test substrate exist; general live next-edit quality/latency and real-provider default behavior are not established as product evidence.
- Precision/acceptance metadata is projected in desktop UI (see `view.rs`); it is not evidence of validated model quality. Ledger PR-AI-001 remains Product workflow validated for inspectability, with that qualification explicitly attached.

## Persistent/resumable agent sessions

- Workflow session shape and coordinator reconstruction exist: `crates/legion-protocol/src/lib.rs` (`LegionWorkflowSession`, `validate_legion_workflow_session`) and `crates/legion-agent/src/lib.rs` (`LegionWorkflowCoordinator::new`). Unit test `legion_workflow_resume_uses_persisted_worker_and_dependency_state` rebuilds a coordinator from a supplied session DTO with completed/ready worker states. App exposes `seed_legion_workflow_sessions` and stores a `legion_workflow_sessions: Vec<LegionWorkflowSession>` in `crates/legion-app/src/lib.rs`; GP-4 evidence covers workflow orchestration, approvals, pause/resume, and replay.
- This demonstrates resumable state semantics when session metadata is supplied, plus in-process app workflow state. It does not by itself prove that agent conversations/execution can be durably saved across app restarts and resumed by a user. The durable store I found, `crates/legion-desktop/src/session.rs` (`DesktopSessionStore`), concerns desktop/editor UI session restoration; it should not be conflated with durable agent-session persistence. No durable agent-session load/save UX or product-readiness gate for that workflow was located in the scoped search. PR-AI-002 remains substrate validated, not a product-session-resume acceptance.

## Settings/keybinding import and VS Code compatibility

- Existing desktop settings/keymap dispatch are native Legion configuration and input behavior, not evidence of importing VS Code user settings or `keybindings.json`. Scoped implementation search found no VS Code settings/keybinding import workflow or importer.
- `crates/legion-vscode-compat/src/lib.rs` parses/normalizes extension `package.json` metadata (`load_open_vsx_extension`, `normalize_manifest`) and classifies activation events/contributions. The `"keybindings"` contribution is classified as Tier 0 declarative metadata; protocol contribution enums include `Keybinding`. That is extension-manifest contribution classification, not migration/import of a user’s VS Code keymap/settings. ADR-0047 (`plans/adrs/ADR-0047-extension-distribution.md`) likewise describes keybindings as declarative extension contributions and says this compat layer does not execute VSIX contents or grant runtime authority.
- Ledger PR-VSC-001 is only Substrate validated: classification/reporting exists, but activation routing and enable/disable/update product workflows are absent, and no shipped composition path uses `legion-vscode-compat` for live VSIX ingestion. PR-VSC-002 runtime extension host is deferred under ADR-0046. Ledger Gate Rules defer extension execution, webviews, notebooks, custom editors, storage and marketplace execution pending separate ADR/policy/sandbox/test evidence. Therefore current compatibility evidence does not establish import parity or a complete VS Code extension workflow.

Decision-relevant gaps to carry into later interviews: whether the scope requires protocol-native ACP interoperability versus the existing local process bridge; what prediction provider/default and measurable usefulness bar is required; whether “resumable session” means desktop/editor restoration, workflow metadata reconstruction, or durable agent execution/conversation recovery; and whether compatibility means importing personal settings/keybindings, consuming declarative extension contributions, or running VS Code extensions. These notes report current evidence only and make no product choice.
