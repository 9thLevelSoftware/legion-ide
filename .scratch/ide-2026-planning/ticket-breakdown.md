# Approved Legion 2026 ticket breakdown

Approved and published — 254 individual local tickets. See the [ticket map](map.md).

This is the approved execution breakdown of the [approved specification](spec.md).
It contains 254 numbered slices. Each keeps the named existing package as its
requirement owner; it is not a new acceptance database. Existing implementation is
reused and qualified, with only observed gaps repaired. No parent specification,
canonical status record, product code, or unrelated WIP is changed by publication.

## Publication

The user approved the granularity and blocking edges. Each entry is published as
its own local issue with `ready-for-agent` status, behavioral acceptance criteria
and linked blocking tickets. Publication is separate from starting implementation
or authorizing provisioning.

The high count reflects the whole retained product program, not only the new AI
features. Language/project/OS qualification is deliberately split into independent
cells. This is not a schedule or a promise that every prerequisite is available.

## Execution rules

- Number order is topological, not priority: execute any approved ticket whose blockers are resolved.
- Native Manual acceptance does not depend on credentials, ACP, formal tools, learned retrieval or release signing.
- Matrix/contract tickets must select named versions and finite scenarios before their dependents run; dependents may not invent arbitrary PATH versions.
- Each implementation slice must demonstrate its narrow complete user path, failure/denial behavior and relevant real external effect. Current substrate is credited without relabeling it product acceptance.
- Use the confirmed AppComposition boundary, native desktop input acceptance and focused process/storage contracts. Select the smallest meaningful check set before editing; run it once, rerunning only affected failures after supported fixes.
- External accounts, test hosts, tool provisioning, signers and human observation are prerequisites, not fake tickets marked done by tests. Record unavailable resources separately from code blockers.
- Contract/ADR changes include their policy, dependency enforcement and contract tests before activation. Allocate unused ADR numbers; older suggested numbers may now collide.
- A discovered gap beyond one fresh-context-sized repair becomes an explicit child repair proposal before closing the owning slice. Aggregate acceptance items collect evidence; they do not hide unbounded implementation.
- Provider cancellation is the intentional wide-refactor exception: expand, migrate independent caller batches, then contract. The old path stays available until every batch lands green; shared files have one coordinator.
- Five pilot working days are distinct from the retained final campaign of ten owner days and two independent usability sessions.
- Implementation, experimental conclusion and supported-delivery status stay separate. Missing equipment is blocked work, not a negative experimental result.
- Deferred AHP hosting, after-exit execution, Git replacement and autonomous deployment receive no implementation ticket.
